# Guest RSVP (pilot)

Lets an organizer collect answers from guests who have not registered for
SquadQuest. The organizer adds each guest by name (and optionally phone) to
one or more of their events, sends each guest a private link, and the guest
answers yes / maybe / no on a plain web page without signing in. An organizer
can also make one **open link** per event, e.g. for a QR code on a printed
flyer: anyone who scans it answers with their phone number and first name in
one screen.

Status: pilot on the v1 production stack. Purely additive.

## Data model

- **`guests`**: `id`, `host` (→ `profiles`, defaults to `auth.uid()`),
  `name` (1–100 chars), `phone` (E.164 or null), `token`, `created_at`.
  `token` is 64 hex characters (two `gen_random_uuid()` values, 244 random
  bits) generated by the database. Hosts may insert only `id, host, name,
  phone` and update only `name, phone`, so a client can never choose or
  change a token. `(host, phone)` is unique when phone is set.
  `claimed_by` (→ `profiles`) and `claimed_at` are set by the database when
  the guest becomes a member; hosts can read them but never write them.
- **`instance_guests`**: primary key `(instance, guest)`; `status` is one of
  `invited | yes | maybe | no` (default `invited`); `updated_at` maintained by
  the shared `set_updated_timestamp()` trigger. Deleting an event or a guest
  deletes the rows. `note` is the guest's optional note for that event:
  null, or 1–200 characters of plain text (see [Guest notes](#guest-notes)).
  `plus` is how many extra people the guest is bringing: 0–9, default 0
  (see [Plus-ones](#plus-ones)).
- **`instance_open_links`**: `token` (primary key, same format as guest
  tokens), `instance`, `created_by`, `created_at`, `closed_at`, `max_guests`
  (default 300), `guests_created`. At most one link per event is open at a
  time; a closed link stays closed (making a new one issues a new token).
- **`guest_rsvp_open_join(token, name, phone, status, note, set_note, plus, set_plus)`**
  (`note` and `plus` default to null, `set_note` and `set_plus` to false; see
  [Guest notes](#guest-notes) and [Plus-ones](#plus-ones)): executable by
  `service_role` only. Locks the link row, checks it is open, the event is
  `live` and the link is not full (see [The open link's cap](#the-open-links-cap)), then finds the host's guest with
  that phone (deduplicated on `(host, phone)`) or creates one, attaches them
  to the event if needed and sets the answer. A reused guest's name is kept
  (filled in only if empty). Returns the guest's token **only when this call
  created the guest**, otherwise NULL, so typing someone's phone number never
  yields their link. A created guest has `guests.open_link` set to the
  link's token. Raises `not_found` or `bad_request`.
- **`guest_rsvp_answer(guest, instance, status, note, set_note, plus, set_plus)`**:
  executable by `service_role` only. A guest's answer through their own
  link; returns false when the guest is not on the event or when raising
  their plus-ones would take the link that created them over its cap.
- **`guest_open_link_plus(token)`**: executable by `service_role` only. The
  plus-ones a link holds (see [The open link's cap](#the-open-links-cap)).

### Row level security

- A host can select / insert / update / delete their own `guests`.
- A host can manage `instance_guests` rows only on events they created, and
  only attach guests that are theirs.
- A host can manage open links only on events they created.
- `anon` has no privileges on any of the three tables. The `guest-rsvp`
  function reads them with the service role, scoped by the caller's token.

## Contract: `guest-rsvp`

`/functions/v1/guest-rsvp`. No user login. CORS: `*`, methods
`GET, POST, OPTIONS`. Every response is JSON with `Cache-Control: no-store`.

### Event object

| key | from `instances` | |
| --- | --- | --- |
| `id` | `id` | uuid |
| `title` | `title` | |
| `start` | `start_time_min` | ISO 8601, UTC |
| `start_max` | `start_time_max` | ISO 8601, UTC: end of the arrival window |
| `end` | `end_time` | ISO 8601 or null |
| `location` | `location_description` | text |
| `notes` | `notes` | text or null |
| `banner` | `banner_photo` | URL or null |
| `event_status` | `status` | `live` or `canceled` (drafts are never returned) |
| `rsvp` | `instance_guests.status` | `invited`, `yes`, `maybe`, `no`; `null` on an open link and for a claimed guest |
| `note` | `instance_guests.note` | the guest's own note for this event, or `null`. `null` wherever `rsvp` is (open-link `GET`, claimed guest). On an open-link `POST`: the note that request set, or `null` if it sent none (see [Guest notes](#guest-notes)) |
| `plus` | `instance_guests.plus` | integer 0–9: extra people coming with the guest, not counting them; `0` when unset. `0` on an open-link `GET` and for a claimed guest. On an open-link `POST`: the `plus` that request sent, or `0` if it sent none. Stored whatever `rsvp` is: count it only when `rsvp` is `yes` or `maybe` (see [Plus-ones](#plus-ones)) |

Events are sorted by `start`. Only events created by the guest's host are
returned.

### Requests

| Request | 200 body |
| --- | --- |
| `GET ?t=<guest token>` | `{guest:{name}, host:{first_name}, events:[Event…], claimed}`. `claimed` is true once the guest has become a member: every `rsvp` is then `null`, and the page should tell them to answer in the app |
| `POST {t, instance, status, note?, plus?}` (`status` = `yes`/`maybe`/`no`) | same as `GET ?t`, read back after the write |
| `GET ?o=<open token>` | `{guest:null, host:{first_name}, events:[Event]}` (one event, `rsvp: null`) |
| `POST {o, phone, name, status, note?, plus?}` | `{created, token, guest:null, host:{first_name}, events:[Event]}`: the one event with `rsvp` = the answer just set, `note` = the note just set (or null) and `plus` = the plus just set (or 0). `created` is true and `token` is the new guest's own token (for `?t=` from then on) only when this request created the guest; otherwise `created: false, token: null`. Never the stored name or other events. |

`OPTIONS` answers 204.

### Errors

Always `{"error": "<code>"}`, nothing else:

| HTTP | code | when |
| --- | --- | --- |
| 400 | `bad_request` | neither or both of `t`/`o`; body not a JSON object; `status` not yes/maybe/no; open-link `name` empty or over 80 chars after trimming; open-link `phone` missing or not a phone number (see below); `note` neither a string nor null, or over 200 characters after cleaning (see [Guest notes](#guest-notes)); `plus` not null and not a JSON integer from 0 to 9 (a fraction, a numeric string, a negative, over 9) |
| 404 | `not_found` | unknown or malformed token; event the guest is not on; canceled or draft event; another host's event; closed open link; open link at its cap, or an answer that would take it over (plus-ones included, see [The open link's cap](#the-open-links-cap)), through the open link or the guest's own link; open link on a canceled event |
| 405 | `method_not_allowed` | any other method |
| 409 | `claimed` | `POST {t,…}` for a claimed guest; `POST {o,…}` whose phone is the host's claimed guest. Nothing is written |
| 413 | `too_large` | body over 2048 bytes |
| 500 | `server_error` | anything unexpected (logged, never echoed) |

Open-link `phone` is normalized by the function: E.164 (`+` then 7–15 digits)
is kept; a US number typed as 10 digits, or 11 starting with `1`, with any
spaces, dots, dashes or parentheses, becomes `+1XXXXXXXXXX`; anything else is
`bad_request`.

Every 404 case is the same response, so a caller cannot tell an unknown token
from an event it is not on.

## Guests who become members

When a guest signs up for SquadQuest, their guest rows are **claimed**: what
they answered as a guest becomes their RSVP in the app, and the host gets a
friend request to them. Everything runs in the database, so no app release is
needed.

### When it runs

- **Automatically, at signup.** The app creates the `profiles` row right
  after the person types their SMS code (`lib/ui/profile_form/profile_form_screen.dart`
  inserts `id` and `phone` = `session.user.phone`). The trigger
  `guest_claim_on_profile_insert` (AFTER INSERT on `profiles`) calls
  `guest_claim_for_user(new.id)`. It catches every error, logs it as a
  `WARNING` in the database log and lets the signup go on; a failed claim is
  rolled back whole and can be run again.
- **By the member, for themself:** `select guest_claim_mine()` (RPC
  `guest_claim_mine`, granted to `authenticated`, only ever acts on
  `auth.uid()`). Covers a host adding the number of someone who is already a
  member. The v1 app does not call it; a future app release could.
- **By the operator**, for people who already had a profile before this was
  deployed (as `postgres`, or RPC with the service role):

  ```sql
  select p.id, public.guest_claim_for_user(p.id) as claimed
  from public.profiles p
  where exists (select 1 from public.guests g
                where g.claimed_by is null
                  and g.phone = '+' || ltrim(p.phone, '+'));
  ```

  `profiles.phone` is only used here to pick candidates; the claim itself
  checks the verified phone (below).

All three are idempotent: claimed guests are skipped and member rows are
inserted with `ON CONFLICT DO NOTHING`, so a second run changes nothing and
returns 0.

### What counts as a verified phone

Never `profiles.phone`: the app writes it and RLS checks only the row's `id`.
The claim reads GoTrue's own tables (`guest_claim_verified_phone()`):

1. `auth.users.phone_confirmed_at` is set, and
2. one of the user's sessions was signed in with a one-time code
   (`auth.mfa_amr_claims.authentication_method = 'otp'`) at or after
   `phone_confirmed_at`, and
3. the account has no email.

Why not `phone_confirmed_at` alone: `docker-compose.yml` passes
`ENABLE_PHONE_AUTOCONFIRM` to `GOTRUE_SMS_AUTOCONFIRM` (`.env.example` sets it
`true`). With it on, GoTrue v2.171.0 sets `phone_confirmed_at` with no SMS at
all on a password signup (`POST /signup {phone, password}`) and on a phone
change (`PUT /user {phone}`). Rule 2 needs a code that GoTrue sent to the
*current* phone: a phone changed after the last code sign-in does not count.
Email codes and magic links are also recorded as `otp`, hence rule 3; the app
signs in by phone only. This was checked against a real GoTrue v2.171.0 with
autoconfirm on and off.

`auth.users.phone` is stored as digits without `+`; the claim compares
`'+' || phone` with `guests.phone` (E.164).

Consequences: the account behind the TEST_PHONE (password sign-in) never
claims. Signing out deletes the session and its `otp` record, so the
operator backfill skips members who have since signed out on every device;
they are claimed if they sign in again and call `guest_claim_mine()`, or not
at all with the v1 app.

### What a claim does

For the user's verified phone, every unclaimed `guests` row with that phone,
**from every host**, is claimed, in one transaction:

1. **RSVPs.** Each `instance_guests` answer on the host's own non-draft events
   (live or canceled) becomes an `instance_members` row for the member, with
   the same status and `created_by` = the host:

   | guest answer | member status |
   | --- | --- |
   | `invited` | `invited` |
   | `yes` | `yes` |
   | `maybe` | `maybe` |
   | `no` | `no` |

   This is the shape the v1 `invite` function writes for a host's invitation
   (`status: "invited"`, `created_by` = the host), so a claimed `invited` is
   an ordinary invitation in the app. Answers keep `created_by` = the host
   too: in the `rsvp` function, a member clearing an RSVP the host created
   sets it back to `invited` instead of deleting it, so a member on a private
   event does not lose access by changing their mind.
   The guest's note for the event goes to `instance_members.note` (see
   [Guest notes](#guest-notes)), with their plus-ones folded in (see
   [Plus-ones](#plus-ones)).
   **An existing member row for the event always wins** and is never changed,
   note included.
   No push notification is sent (nothing fires on `instance_members` inserts;
   v1 notifies from the functions).
2. **Friend request.** If no `friends` row exists between the host and the
   member in either direction, the host gets a pending request
   (`requester` = host, `requestee` = member, `status` = `requested`), the
   same row `on-profile-insert` creates for people invited by phone through
   `send-friend-request`. The member accepts or declines in the app. Skipped
   when the host is the member, and when the host is in the user's
   `app_metadata.invite_friends`: `on-profile-insert` creates that request
   itself after the signup commits, with a batch upsert that would fail on a
   row already there.
3. **Mark.** `claimed_by` = the member, `claimed_at` = now. The guest's own
   `instance_guests` rows are kept as they were.

The member rows and friend request a claim makes have `created_at` equal to
the guest's `claimed_at` (one transaction), which is how the rollback below
finds them.

### Guest links after a claim

The private link keeps working **read-only**: `GET ?t=` still lists the
host's events, with `claimed: true` and every `rsvp` null, and `POST` answers
`409 {"error":"claimed"}` without writing. The open link answers the same 409
when the phone typed is the host's claimed guest.

Chosen over writing through to the member row because the link is a bearer
credential (anyone it was forwarded to could change a real member's RSVP),
because an open-link caller has proven only that they know a phone number,
and because a write-through would bypass the `rsvp` function's access checks
and notifications. Showing no answer avoids showing one that has since
changed in the app. The microsite should show "You're on SquadQuest now:
answer in the app" when `claimed` is true or on a 409; until it does, a 409
shows as its generic error.

The open-link check happens in the function just before
`guest_rsvp_open_join()`, not inside it, so an answer that races a claim to
the same row can still land on the guest row. It changes nothing in the app.

### Row level security

Unchanged. A member can never read `guests` or `instance_guests`, including
rows they claimed. A host still sees only their own guests and now sees
`claimed_by` / `claimed_at`, but cannot write either. `guest_claim_for_user`
and `guest_claim_verified_phone` are not executable by `anon` or
`authenticated`. All four functions are `SECURITY DEFINER` with
`search_path = public, pg_temp`.

### Deploy

After the guest RSVP objects above are live and this branch is merged to
`v1`. Order matters: the new `guest-rsvp` reads `guests.claimed_at`, and the
host serves functions straight from the checkout, so apply the SQL **before**
pulling, or every guest link answers 500 in between.

1. Back up: `docker compose exec -T db pg_dump -U postgres -Fc postgres > ~/pre-guest-claim-$(date +%F).dump`
2. Check the claim can read GoTrue's tables (expect `t|t|t`):
   `docker compose exec -T db psql -U postgres -tAc "select has_table_privilege('auth.users','select'), has_table_privilege('auth.sessions','select'), has_table_privilege('auth.mfa_amr_claims','select')"`
3. Apply from the fetched branch, in one transaction:

   ```bash
   git fetch origin
   git show origin/v1:supabase/tables/instance_guests_claim.sql \
     | docker compose exec -T db psql -v ON_ERROR_STOP=1 --no-password --no-psqlrc \
         -U postgres --single-transaction
   docker compose exec -T db psql -U postgres -c "NOTIFY pgrst, 'reload schema'"
   ```

4. `git pull` on `v1`. The new `guest-rsvp` is live from the next request.
5. Optionally run the operator backfill above and note the counts.
6. Smoke test: sign up a test account by SMS code with a number that is a
   guest of yours; check `guests list` shows it claimed, the RSVP shows in
   the app, the friend request arrives, and the guest link shows
   `claimed: true`.

### Rollback

1. Stop new claims, keep everything else:
   `drop trigger guest_claim_on_profile_insert on public.profiles;`
2. Optionally remove what claims made. This deletes RSVPs the member may
   since have changed in the app and pending friend requests; accepted ones
   are kept:

   ```sql
   delete from public.instance_members im using public.guests g
   where im.member = g.claimed_by and im.created_by = g.host
     and im.created_at = g.claimed_at;
   delete from public.friends f using public.guests g
   where f.requestee = g.claimed_by and f.requester = g.host
     and f.created_at = g.claimed_at and f.status = 'requested';
   ```

3. Drop the objects in one transaction (if `guest-rsvp` is still deployed
   from this branch, revert it first: it reads `claimed_at`):

   ```bash
   docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres --single-transaction -c "
     drop trigger if exists guest_claim_on_profile_insert on public.profiles;
     drop function public.guest_claim_on_profile_insert();
     drop function public.guest_claim_mine();
     drop function public.guest_claim_for_user(uuid);
     drop function public.guest_claim_verified_phone(uuid);
     drop index public.guests_phone_unclaimed_idx;
     alter table public.guests drop column claimed_at, drop column claimed_by;"
   docker compose exec -T db psql -U postgres -c "NOTIFY pgrst, 'reload schema'"
   ```

   Once the columns are gone, claimed guests are ordinary guests again and
   their links accept answers.

## Guest notes

A guest can leave a short note with their answer ("bringing a friend",
"running late"). Hosts see it next to the answer (`guests list` in the CLI).

### Rules

`note` is optional in both `POST` bodies:

| `note` in the body | effect |
| --- | --- |
| absent | the stored note is left as it is, so a one-tap status change never wipes it |
| `null`, `""`, or only whitespace / control characters | the note is cleared |
| a string | cleaned, then stored |
| a string over 200 characters after cleaning | `400 bad_request`, nothing written |
| anything else (number, boolean, array, object) | `400 bad_request`, nothing written |

Cleaning, in the function: lone UTF-16 surrogates become U+FFFD; control
characters are removed (C0 except newline, DEL, C1; so `\r\n` becomes `\n`);
then the string is trimmed. Length is counted in characters (code points),
the same way as `char_length()` in the database. Newlines are kept; nothing
is collapsed or escaped. It is plain text: clients must render it as text,
never as HTML.

Storage: `instance_guests.note`, nullable, check `char_length(note) between 1
and 200`. `guest_rsvp_open_join()` trims it again, stores an empty one as
null and raises `bad_request` over 200.

Who sees it:

- the guest, on their own link (`GET ?t`, `POST {t,…}`);
- the host, through the existing select grant and RLS policy on
  `instance_guests` ("Hosts can read guests on their own events"); no other
  member, and not `anon`. Hosts can also write it through the same update
  grant they already had on `instance_guests`; the CLI does not;
- an open-link caller sees **only the note their own request set**, never a
  stored one: the caller has proved only that they know a phone number, the
  same reason they never get the stored name or token. A status-only open-link
  post from a known phone keeps the stored note but answers `note: null`;
- a claimed guest's link shows `note: null`, like `rsvp`.

On a claim, the guest's note for each event is copied to
`instance_members.note` (free text, no constraint there) when the claim
creates the member row. An existing member row wins whole, its note
included.

### Deploy

Backward compatible in both directions: the `guest-rsvp` function from
before this change keeps working against the new SQL (its 4-argument RPC call
resolves to the new function with `note` and `set_note` defaulted, and it
never reads the column). The new function needs the new SQL (it selects
`instance_guests.note` and passes `p_note` / `p_set_note`). So apply the SQL
**before** pulling, as for the claim.

Run on the production host, from the v1 checkout's `supabase/` directory,
after this branch is merged to `v1`. Needs the guest RSVP objects and the
claim objects above already applied.

1. Back up: `docker compose exec -T db pg_dump -U postgres -Fc postgres > ~/pre-guest-note-$(date +%F).dump`
2. Apply from the fetched branch, in one transaction:

   ```bash
   git fetch origin
   git show origin/v1:supabase/tables/instance_rsvp_notes.sql \
     | docker compose exec -T db psql -v ON_ERROR_STOP=1 --no-password --no-psqlrc \
         -U postgres --single-transaction
   docker compose exec -T db psql -U postgres -c "NOTIFY pgrst, 'reload schema'"
   ```

3. `git pull` on `v1`. The new `guest-rsvp` is live from the next request.
4. Smoke test: open a test guest's link, answer with a note, change the
   answer without one, and check `guests list` shows the note both times.

### Rollback

1. Revert the merge on `v1` and `git pull`: the old function ignores notes and

## Plus-ones

A guest can say how many extra people are coming with them. Hosts see it
next to the answer, with a headcount per event (`guests list` in the CLI).

### Rules

`plus` is optional in both `POST` bodies:

| `plus` in the body | effect |
| --- | --- |
| absent | the stored value is left as it is, so a one-tap status change never resets it |
| `null` or `0` | set to 0 |
| a JSON integer 1–9 | stored |
| anything else: a fraction, a numeric string (`"2"`), a negative, over 9, a boolean, an array, an object | `400 bad_request`, nothing written |

Storage: `instance_guests.plus smallint not null default 0`, check `plus
between 0 and 9`. The value is kept when the answer changes, including to
`no`: it is not zeroed. Readers decide, and every reader here counts it only
for `yes` and `maybe`: the cap, the claim and the CLI headcount.

Who sees it: the same as the note. The guest on their own link; the host
through their existing grants and policy on `instance_guests`; an open-link
caller sees **only the `plus` their own request sent** (or 0), never a stored
one; a claimed guest's link and an open-link `GET` show 0.

### The open link's cap

Before this change `max_guests` counted only the guests a link **created**
(`guests_created`): a phone already on the host's list did not count, and a
link with `guests_created >= max_guests` answered 404 to everyone.

Now a link holds `guests_created` plus the plus-ones of the guests it
created, on its own event, while their answer is `yes` or `maybe`
(`guest_open_link_plus(token)`). A guest records the link that created them in
`guests.open_link`, set by `guest_rsvp_open_join()` and never writable by
hosts.

- The link is **full** when `guests_created + plus-ones held >= max_guests`.
  A full link answers 404 to everyone, `GET ?o=` included, as before.
- An open-link `POST` that would take the link **over** `max_guests` is the
  same 404 and writes nothing (no guest is created). That covers a new guest
  whose `1 + plus` does not fit, and an existing link guest raising `plus` or
  switching a `no` with plus-ones to `yes`.
- A link guest's own link (`POST {t,…}`, through `guest_rsvp_answer()`)
  answers the same 404 when the change would raise the plus-ones held past
  `max_guests`, whether or not the link is still open; lowering is always
  allowed. Without this, joining with `plus: 0` and raising it afterwards
  would bypass the cap.
- Plus-ones of guests the link did not create (a host-added guest answering
  through the flyer, or a guest another link created) do not count, the same
  way those guests themselves never counted.
- Guests created through a link before this change have no `open_link`, so
  their plus-ones never count. All of them had 0 plus-ones when it was
  applied.

All of this runs under the link row lock, so concurrent answers cannot
overshoot.

### Claim

`instance_members` has no plus-ones field and none is added. When a claim
creates the member row and the guest answered `yes` or `maybe` with `plus >
0`, the member note is the guest's note followed by ` (+N)`, or `+N` when
there is no note (`Bringing chips (+2)`, `+1`). `instance_members.note` has
no length limit, and a guest note is at most 200 characters, so this never
truncates. Plus-ones on an `invited` or `no` answer are not copied: in the
app they would read as people coming. An existing member row still wins
whole.

### Deploy

Backward compatible in both directions: the `guest-rsvp` function from
before this change keeps working against the new SQL (its 6-argument RPC call
resolves to the new 8-argument join with `plus` and `set_plus` defaulted,
which leave the stored value alone; it updates answers with a plain `UPDATE`
that never touches `plus`; it never reads `plus` or `open_link`). It does not
enforce the plus-ones part of the cap. The new function needs the new SQL (it
selects `plus` and calls `guest_rsvp_answer` and `guest_open_link_plus`), so
apply the SQL **before** pulling.

Run on the production host, from the v1 checkout's `supabase/` directory,
after this branch is merged to `v1`. Needs the guest RSVP, claim and note
objects above already applied: this file comes **after**
`instance_rsvp_notes.sql` and **before** `git pull`.

1. Back up: `docker compose exec -T db pg_dump -U postgres -Fc postgres > ~/pre-guest-plus-$(date +%F).dump`
2. Apply from the fetched branch, in one transaction:

   ```bash
   git fetch origin
   git show origin/v1:supabase/tables/instance_rsvp_plus.sql \
     | docker compose exec -T db psql -v ON_ERROR_STOP=1 --no-password --no-psqlrc \
         -U postgres --single-transaction
   docker compose exec -T db psql -U postgres -c "NOTIFY pgrst, 'reload schema'"
   ```

3. `git pull` on `v1`. The new `guest-rsvp` is live from the next request.
4. Smoke test: open a test guest's link, answer yes with `plus: 2`, change the
   answer without `plus`, and check `guests list` shows `+2` and the
   headcount both times.

### Rollback

1. Revert the merge on `v1` and `git pull`: the old function ignores
   plus-ones and works against the new SQL. Stored plus-ones stay in the
   column; the cap counts only created guests again, as far as the old
   function checks it (the join itself still counts plus-ones until step 2).
2. Optionally remove the SQL too (deletes every stored plus-one and which link
   created each guest; notes folded into `instance_members.note` stay). This
   restores the two functions from the commit before plus-ones (`13174a4`)
   in one transaction:

   ```bash
   { echo "drop function public.guest_rsvp_answer(uuid, uuid, text, text, boolean, integer, boolean);"
     echo "drop function public.guest_rsvp_open_join(text, text, text, text, text, boolean, integer, boolean);"
     echo "drop function public.guest_open_link_plus(text);"
     git show 13174a4:supabase/tables/instance_rsvp_notes.sql \
       | sed -n '/^CREATE FUNCTION public.guest_rsvp_open_join/,/^-- 3\. A claim/p' | sed '$d'
     git show 13174a4:supabase/tables/instance_rsvp_notes.sql \
       | sed -n '/^CREATE OR REPLACE FUNCTION public.guest_claim_for_user/,$p'
     echo "alter table public.guests drop column open_link;"
     echo "alter table public.instance_guests drop column plus;"
   } | docker compose exec -T db psql -v ON_ERROR_STOP=1 --no-password --no-psqlrc \
         -U postgres --single-transaction
   docker compose exec -T db psql -U postgres -c "NOTIFY pgrst, 'reload schema'"
   ```

   Run step 1 first: the new function calls the dropped functions. The
   index and foreign key on `open_link` go with the column. Checked on a
   local database: the 6-argument join and its grants come back, and the
   claim no longer mentions plus-ones.

## How SQL and functions reach production on v1

There is no migration tool and no deploy workflow on `v1`
(`.github/workflows/` only builds the app). `supabase/tables/*.sql` and
`supabase/policies/*.sql` are the declarative definition used by
`supabase/squadquest-init.sh` for a fresh database; changes to a running
database are applied by hand with `psql` in the `db` container. Edge
functions are served from the `./functions` directory, bind-mounted into the
`functions` (edge-runtime) container; the `main` router starts a worker per
request from `/home/deno/functions/<name>`, so a new function directory is
live as soon as it exists on the host.

JWT checking for functions is global, not per function:
`VERIFY_JWT: "${FUNCTIONS_VERIFY_JWT}"` in `docker-compose.yml`
(`.env.example` sets `false`). If production has it `true`, every call to
`guest-rsvp` must carry `Authorization: Bearer <anon key>`; the anon key is
public (it ships in the web app), and the microsite has a constant for it.

## Deploy to production

Run on the production host, from the v1 checkout's `supabase/` directory,
after this branch is merged to `v1`.

1. Update the checkout: `git pull` on `v1`. This makes
   `functions/guest-rsvp/` exist on the host.
2. Back up the schema and data:
   `docker compose exec -T db pg_dump -U postgres -Fc postgres > ~/pre-guest-rsvp-$(date +%F).dump`
3. Apply the new objects in one transaction:

   ```bash
   cat tables/guests.sql tables/instance_guests.sql tables/instance_open_links.sql \
       policies/guests.sql policies/instance_guests.sql policies/instance_open_links.sql \
     | docker compose exec -T db psql -v ON_ERROR_STOP=1 --no-password --no-psqlrc \
         -U postgres --single-transaction
   ```

4. Reload the API schema cache so the new tables and the RPC are visible:
   `docker compose exec -T db psql -U postgres -c "NOTIFY pgrst, 'reload schema'"`
5. Check which JWT mode the functions run in:
   `grep FUNCTIONS_VERIFY_JWT .env`. If `true`, set the microsite's `ANON_KEY`
   constant to the anon key the web app publishes (the legacy one, which is
   the key production accepts).
6. Smoke test with a token that cannot exist; expect `404 {"error":"not_found"}`
   and an `access-control-allow-origin: *` header:
   `curl -si "https://supabase.squadquest.app/functions/v1/guest-rsvp?t=$(printf '0%.0s' {1..64})"`
7. As the organizer, add one test guest to one of your own events with the
   CLI, open their link, answer, and check the answer with `guests list`.
   Then remove the test guest.
8. Publish the microsite with `API_BASE` set to
   `https://supabase.squadquest.app/functions/v1/guest-rsvp`.

## Rollback

Each step stands alone; stop at the one that is enough.

1. Take the microsite down or replace it with a "text the host" page.
2. Close every open link (`guests open-link --event <id> --close`) if only
   the flyer flow is the problem.
3. Export what guests answered, if it is wanted:
   `docker compose exec -T db psql -U postgres -c "\copy (select g.name, g.phone, ig.instance, ig.status, ig.updated_at from guests g join instance_guests ig on ig.guest = g.id) to stdout csv header" > ~/guest-rsvp-answers.csv`
4. Drop the new objects in one transaction. If the objects from
   [Plus-ones](#plus-ones) are deployed, run their rollback first, then the
   one from [Guest notes](#guest-notes), then the one from
   [Guests who become members](#guests-who-become-members).

   ```bash
   docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres --single-transaction -c "
     drop function public.guest_rsvp_open_join(text, text, text, text);
     drop table public.instance_open_links;
     drop table public.instance_guests;
     drop table public.guests;"
   docker compose exec -T db psql -U postgres -c "NOTIFY pgrst, 'reload schema'"
   ```

   Policies, indexes and the trigger go with their tables. No existing object
   depends on them.
5. Remove `functions/guest-rsvp/` (revert the merge on `v1` and `git pull` on
   the host). Until then it answers 500 for every request once the tables are
   gone, and exposes nothing.

## Testing

- **Function**: `deno test supabase/functions/guest-rsvp/handler.test.ts`
  (in-memory store, no network). Without a local Deno:
  `docker run --rm --network none -v "$PWD/supabase/functions:/fn:ro" -w /fn denoland/deno:2.1.4 test --no-remote guest-rsvp/handler.test.ts`

  loaded (`./squadquest-init.sh` on the local stack):
  `docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres < tests/guests_rls.sql`.
  The script runs in a transaction it rolls back and prints
  `guests_rls: all checks passed`.

- **Plus-ones**: same way, `< tests/guests_plus.sql`; prints
  `guests_plus: all checks passed`. Needs GoTrue's tables like the claim test.

## Known risks

- **The link is the credential.** Anyone holding a guest link can see that
  guest's events (title, time, place, notes) and change their answer. Tokens
  carry 244 random bits and are only returned to their host (or, for an open-link join, to the person who
  joined), but a forwarded
  link works for whoever has it.
- **Tokens in URLs reach logs.** `GET ?t=` puts the token in gateway and
  analytics logs. The microsite sets `referrer` to `no-referrer` so it does
  not leak to image hosts.
- **Open links are open.** Anyone with the flyer can add any name and number.
  The cap (300 people per link by default: new guests plus their plus-ones,
  see [The open link's cap](#the-open-links-cap)) bounds the damage; closing the
  link stops it. There is no per-IP rate limit. A full link answers 404 for
  everyone, including people already on the list.
- **No phone verification.** There is no SMS, no code and no check that the
  person owns the number they type. Anyone with the flyer can answer as any
  phone number, including changing the answer of someone already on the list
  for that event, and setting or clearing their note and plus-ones for it.
  They never get that person's link, name, note, plus-ones or other events.
  Accepted for a pilot: the host sees the whole list with `guests list` and
  can remove anyone.
- **Timing**: the 404 cases take slightly different paths; response bodies
  are identical but response times are not constant.
- **Global JWT setting**: see above. If `FUNCTIONS_VERIFY_JWT` is `true` and
  the microsite has no anon key, every call answers 401.
- **Answers do not notify the host** and guests do not appear in the app;
  the host checks with the CLI. A claim does not notify anyone either; the
  member sees the RSVPs and the friend request next time they open the app.
- **A claim gives the member every event the host put them on**, private
  ones included, as a host's invitation would. The phone proof above is what
  stands between a guest list and someone else's account.
- **Past events** can still be answered while `live`.
