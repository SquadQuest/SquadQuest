# Guest RSVP (pilot)

Lets an organizer collect answers from guests who have not registered for
SquadQuest. The organizer adds each guest by name (and optionally phone) to
one or more of their events, sends each guest a private link, and the guest
answers yes / maybe / no on a plain web page without signing in. An organizer
can also make one **open link** per event, e.g. for a QR code on a printed
flyer, so anyone can add themselves.

Status: pilot on the v1 production stack. Purely additive.

## What it adds

| Object | File |
| --- | --- |
| table `guests` | `supabase/tables/guests.sql` |
| table `instance_guests` | `supabase/tables/instance_guests.sql` |
| table `instance_open_links` + function `guest_rsvp_open_join()` | `supabase/tables/instance_open_links.sql` |
| RLS policies for the three tables | `supabase/policies/{guests,instance_guests,instance_open_links}.sql` |
| edge function `guest-rsvp` | `supabase/functions/guest-rsvp/` |
| RLS test | `supabase/tests/guests_rls.sql` |
| function tests | `supabase/functions/guest-rsvp/handler.test.ts` |

Nothing existing changes. No existing table, policy, view, trigger or function
refers to the new objects, so the v1 app never receives a row it does not
expect: guests are deliberately **not** `instance_members` rows, because
`instance_members.member` must be a profile and every v1 client reads that
table. Guests do not appear in the app. Nothing here sends a text message or
a push notification.

## Data model

- **`guests`**: `id`, `host` (→ `profiles`, defaults to `auth.uid()`),
  `name` (1–100 chars), `phone` (E.164 or null), `token`, `created_at`.
  `token` is 64 hex characters (two `gen_random_uuid()` values, 244 random
  bits) generated by the database. Hosts may insert only `id, host, name,
  phone` and update only `name, phone`, so a client can never choose or
  change a token. `(host, phone)` is unique when phone is set.
- **`instance_guests`**: primary key `(instance, guest)`; `status` is one of
  `invited | yes | maybe | no` (default `invited`); `updated_at` maintained by
  the shared `set_updated_timestamp()` trigger. Deleting an event or a guest
  deletes the rows.
- **`instance_open_links`**: `token` (primary key, same format as guest
  tokens), `instance`, `created_by`, `created_at`, `closed_at`, `max_guests`
  (default 300), `guests_created`. At most one link per event is open at a
  time; a closed link stays closed (making a new one issues a new token).
- **`guest_rsvp_open_join(token, name, phone, status)`**: executable by
  `service_role` only. Locks the link row, checks it is open, the event is
  `live` and `guests_created < max_guests`, creates the guest for the event's
  host, attaches them with the answer, counts them, and returns the new
  guest's token. Raises `not_found`, `conflict` (phone already on that host's
  list) or `bad_request`.

### Row level security

- A host can select / insert / update / delete their own `guests`.
- A host can manage `instance_guests` rows only on events they created, and
  only attach guests that are theirs.
- A host can manage open links only on events they created.
- `anon` has no privileges on any of the three tables. The `guest-rsvp`
  function reads them with the service role, scoped by the caller's token.

## Contract: `guest-rsvp`

`/functions/v1/guest-rsvp`. No user login. CORS: `*`, methods
`GET, POST, OPTIONS`. Every response is JSON with `Cache-Control: no-store`.

### Event object

| key | from `instances` | |
| --- | --- | --- |
| `id` | `id` | uuid |
| `title` | `title` | |
| `start` | `start_time_min` | ISO 8601, UTC |
| `start_max` | `start_time_max` | ISO 8601, UTC: end of the arrival window |
| `end` | `end_time` | ISO 8601 or null |
| `location` | `location_description` | text |
| `notes` | `notes` | text or null |
| `banner` | `banner_photo` | URL or null |
| `event_status` | `status` | `live` or `canceled` (drafts are never returned) |
| `rsvp` | `instance_guests.status` | `invited`, `yes`, `maybe`, `no`; `null` on an open link |

Events are sorted by `start`. Only events created by the guest's host are
returned.

### Requests

| Request | 200 body |
| --- | --- |
| `GET ?t=<guest token>` | `{guest:{name}, host:{first_name}, events:[Event…]}` |
| `POST {t, instance, status}` (`status` = `yes`/`maybe`/`no`) | same as `GET ?t`, read back after the write |
| `GET ?o=<open token>` | `{guest:null, host:{first_name}, events:[Event]}` (one event, `rsvp: null`) |
| `POST {o, name, phone?, status}` | `{token, guest:{name}, host:{first_name}, events:[Event]}`: `token` is the new guest's own token, for `?t=` from then on |

`OPTIONS` answers 204.

### Errors

Always `{"error": "<code>"}`, nothing else:

| HTTP | code | when |
| --- | --- | --- |
| 400 | `bad_request` | neither or both of `t`/`o`; body not a JSON object; `status` not yes/maybe/no; open-link `name` empty or over 80 chars after trimming; `phone` not E.164 |
| 404 | `not_found` | unknown or malformed token; event the guest is not on; canceled or draft event; another host's event; closed open link; open link at its cap; open link on a canceled event |
| 405 | `method_not_allowed` | any other method |
| 409 | `conflict` | open-link join with a phone already on that host's guest list (no token is returned) |
| 413 | `too_large` | body over 2048 bytes |
| 500 | `server_error` | anything unexpected (logged, never echoed) |

Every 404 case is the same response, so a caller cannot tell an unknown token
from an event it is not on.

## How SQL and functions reach production on v1

There is no migration tool and no deploy workflow on `v1`
(`.github/workflows/` only builds the app). `supabase/tables/*.sql` and
`supabase/policies/*.sql` are the declarative definition used by
`supabase/squadquest-init.sh` for a fresh database; changes to a running
database are applied by hand with `psql` in the `db` container. Edge
functions are served from the `./functions` directory, bind-mounted into the
`functions` (edge-runtime) container; the `main` router starts a worker per
request from `/home/deno/functions/<name>`, so a new function directory is
live as soon as it exists on the host.

JWT checking for functions is global, not per function:
`VERIFY_JWT: "${FUNCTIONS_VERIFY_JWT}"` in `docker-compose.yml`
(`.env.example` sets `false`). If production has it `true`, every call to
`guest-rsvp` must carry `Authorization: Bearer <anon key>`; the anon key is
public (it ships in the web app), and the microsite has a constant for it.

## Deploy to production

Run on the production host, from the v1 checkout's `supabase/` directory,
after this branch is merged to `v1`.

1. Update the checkout: `git pull` on `v1`. This makes
   `functions/guest-rsvp/` exist on the host.
2. Back up the schema and data:
   `docker compose exec -T db pg_dump -U postgres -Fc postgres > ~/pre-guest-rsvp-$(date +%F).dump`
3. Apply the new objects in one transaction:

   ```bash
   cat tables/guests.sql tables/instance_guests.sql tables/instance_open_links.sql \
       policies/guests.sql policies/instance_guests.sql policies/instance_open_links.sql \
     | docker compose exec -T db psql -v ON_ERROR_STOP=1 --no-password --no-psqlrc \
         -U postgres --single-transaction
   ```

4. Reload the API schema cache so the new tables and the RPC are visible:
   `docker compose exec -T db psql -U postgres -c "NOTIFY pgrst, 'reload schema'"`
5. Check which JWT mode the functions run in:
   `grep FUNCTIONS_VERIFY_JWT .env`. If `true`, set the microsite's `ANON_KEY`
   constant to the anon key the web app publishes (the legacy one, which is
   the key production accepts).
6. Smoke test with a token that cannot exist; expect `404 {"error":"not_found"}`
   and an `access-control-allow-origin: *` header:
   `curl -si "https://supabase.squadquest.app/functions/v1/guest-rsvp?t=$(printf '0%.0s' {1..64})"`
7. As the organizer, add one test guest to one of your own events with the
   CLI, open their link, answer, and check the answer with `guests list`.
   Then remove the test guest.
8. Publish the microsite with `API_BASE` set to
   `https://supabase.squadquest.app/functions/v1/guest-rsvp`.

## Rollback

Each step stands alone; stop at the one that is enough.

1. Take the microsite down or replace it with a "text the host" page.
2. Close every open link (`guests open-link --event <id> --close`) if only
   the flyer flow is the problem.
3. Export what guests answered, if it is wanted:
   `docker compose exec -T db psql -U postgres -c "\copy (select g.name, g.phone, ig.instance, ig.status, ig.updated_at from guests g join instance_guests ig on ig.guest = g.id) to stdout csv header" > ~/guest-rsvp-answers.csv`
4. Drop the new objects in one transaction:

   ```bash
   docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres --single-transaction -c "
     drop function public.guest_rsvp_open_join(text, text, text, text);
     drop table public.instance_open_links;
     drop table public.instance_guests;
     drop table public.guests;"
   docker compose exec -T db psql -U postgres -c "NOTIFY pgrst, 'reload schema'"
   ```

   Policies, indexes and the trigger go with their tables. No existing object
   depends on them.
5. Remove `functions/guest-rsvp/` (revert the merge on `v1` and `git pull` on
   the host). Until then it answers 500 for every request once the tables are
   gone, and exposes nothing.

## Testing

- **Function**: `deno test supabase/functions/guest-rsvp/handler.test.ts`
  (in-memory store, no network). Without a local Deno:
  `docker run --rm --network none -v "$PWD/supabase/functions:/fn:ro" -w /fn denoland/deno:2.1.4 test --no-remote guest-rsvp/handler.test.ts`
- **RLS and the join function**: against a local database with the schema
  loaded (`./squadquest-init.sh` on the local stack):
  `docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres < tests/guests_rls.sql`.
  The script runs in a transaction it rolls back and prints
  `guests_rls: all checks passed`.

## Known risks

- **The link is the credential.** Anyone holding a guest link can see that
  guest's events (title, time, place, notes) and change their answer. Tokens
  carry 244 random bits and are only returned to their host (or, for an open-link join, to the person who
  joined), but a forwarded
  link works for whoever has it.
- **Tokens in URLs reach logs.** `GET ?t=` puts the token in gateway and
  analytics logs. The microsite sets `referrer` to `no-referrer` so it does
  not leak to image hosts.
- **Open links are open.** Anyone with the flyer can add any name. The cap
  (300 per link by default) bounds the damage; closing the link stops it.
  There is no per-IP rate limit.
- **`conflict` reveals that a phone is on the host's list** to whoever types
  it into an open-link form. It does not reveal the guest's link or name.
- **Timing**: the 404 cases take slightly different paths; response bodies
  are identical but response times are not constant.
- **Global JWT setting**: see above. If `FUNCTIONS_VERIFY_JWT` is `true` and
  the microsite has no anon key, every call answers 401.
- **Answers do not notify the host** and guests do not appear in the app;
  the host checks with the CLI.
- **Past events** can still be answered while `live`.
